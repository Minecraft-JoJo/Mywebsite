数据泄漏

一个诡异的分数

你把划分做对了，交叉验证也做了，模型在验证集上拿到 0.95。

上线之后，真实准确率只有 0.6。

中间没有任何改动。模型没变、数据没变、代码没变。那 0.35 去哪了？

数据泄漏（data leakage）

验证集的信息，通过某条你没注意到的路径，渗进了训练过程。

于是你的验证分数衡量的是"模型见过的东西"，不是"模型没见过的东西"。它被系统性地高估了。

三个最常见的来源

一、先标准化，再划分

这是最经典的一个：

# 错误做法
from sklearn.preprocessing import StandardScaler
scaler = StandardScaler()
X_scaled = scaler.fit_transform(X)      # ← 用了全部数据算均值和标准差
X_tr, X_te, y_tr, y_te = train_test_split(X_scaled, y, test_size=0.2)

问题在于 fit_transform(X) 这一步：它用全部样本（包括即将成为测试集的那些）算出了均值和标准差。

于是测试集的均值信息，通过 scaler 流进了训练数据。模型在训练时就已经"知道"测试集长什么样了。

正确做法是先划分，再只用训练集 fit：

# 正确做法
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2)
scaler = StandardScaler()
X_tr = scaler.fit_transform(X_tr)   # 只在训练集上学
X_te = scaler.transform(X_te)       # 用训练集的参数转换，不重新 fit

注意第二行是 transform 不是 fit_transform。这个区别就是全部。

一句话记住

任何"从数据里算出参数"的操作，都只能在训练集上做。

标准化（均值、标准差）、缺失值填充（中位数）、特征选择、PCA、过采样——全是这一类。

它们都得包在训练集里面，然后原样套到验证集上。工程上这叫 pipeline，第 14 章会讲怎么用代码自动保证这件事。

二、特征选择用了全量数据

# 错误做法
best_features = select_by_correlation(X, y, k=10)   # 用全部 200 个样本挑
X_tr, X_te = train_test_split(X[:, best_features], ...)

你在全量数据上挑了"和 y 最相关的 10 个特征"，然后才划分。

问题是：那些特征之所以被挑中，部分原因是它们在测试集上也碰巧表现好。测试集参与了选择，就不再是"没见过的数据"了。

正确做法：把特征选择放进交叉验证的每一折里。

三、时间序列被打乱

# 错误做法
idx = shuffle(range(len(df)))

如果你在预测"明天会不会下雨"，随机打乱之后，训练集里就混进了"下周的数据"。

模型学到的其实是"从未来推过去"——这在真实场景里根本不可能。

时间序列必须按时间顺序切：用前面的预测后面的，绝不能反。

还有一类：目标泄漏

这一类最隐蔽，因为它根本不在代码里，而在特征的定义里。

举个例子：要预测"患者是否患有某种病"，特征里有一条叫"是否服用了该病的特效药"。

这个特征和标签高度相关——相关系数可能 0.9 以上。训练出来的模型准确率极高。

但它是结果，不是原因。等你想用这个模型做早期筛查时，病人还没吃药呢，这个特征根本拿不到。

目标泄漏的判断方法

问自己一个问题：

这个特征，在"做预测的那一刻"，真的拿得到吗？

  • 预测房价时，"成交价"当然拿不到——但它不能当特征
  • 预测用户会不会流失时，"注销时间"拿不到
  • 预测贷款违约时，"催收记录"是在违约之后才有的

凡是要等到结果发生之后才知道的信息，都不能当特征。

怎么发现泄漏

信号说明
验证分数好得可疑比同类问题的合理水平高出一大截
分数高得离谱（0.99+）真实的业务问题很少有这种数字
上线后断崖式下跌这是泄漏的典型症状
某个特征重要得异常单独一个特征的权重远超其他所有

第一条最关键。当你觉得"这个结果太好了"的时候，先怀疑泄漏，再高兴。
