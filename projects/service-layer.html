应用服务与数据层

Backend · Data · Auth · FastAPI / SQLAlchemy / PostgreSQL

这一份的体量最小，也最容易被讲错。它由两条互不相连的链组成：一条是 FastAPI 的模板入口，一条是「建用户 → 哈希 → 落库」的写入链。加起来 139 行，覆盖的是同一个问题——连接、会话与密钥该放在哪一层。

形态
服务底座：连接与会话、密码哈希、令牌签发、模板入口
规模
5 个 Python 文件 / 139 行（users/ 4 文件 125 行 + main.py 14 行）
栈
FastAPI · uvicorn · Jinja2 · SQLAlchemy 2.x · psycopg · PostgreSQL
鉴权
passlib bcrypt 存哈希，python-jose 签 JWT；密钥全部取自环境变量
连接
pool_pre_ping=True 取连接前探活，connect_timeout=3（auth_db.py:17）
不计入

01任务与边界

要交付的是一个可以照着搭的服务底座，不是一套业务系统。底座上只有四件事：怎么连数据库、一次请求用哪个会话、密码以什么形态落库、令牌怎么签发与解析；再加一个能跑起来的最小入口，用来确认前面四件事被正确装配。

先划清口径，因为这页最容易被误读：

  • 服务代码 = 5 个文件 139 行。users/ 下 4 个文件合计 125 行（auth_db.py 52、auth_utils.py 49、creat_user.py 24、__init__.py 0），加 live/main.py 14 行。live/1.py 42 行是草稿，不计入。
  • 7,994 行是 FastAPI 文档，不是实现。那是学习时写的笔记体量，和上面 139 行是两回事。把两者放在同一个数字里说事，会让「我写了七千多行服务」这种误读成立——所以这一页从头到尾只把它们分开记。
  • 不做的：没有业务路由表，没有 ORM 关系的级联策略，没有迁移工具，没有部署编排。live/main.py 里只有一个 "/" 的模板路由（:9-12）。

边界之内，代码是有主张的：连接串、账号、密钥一律通过 load_dotenv() + os.getenv() 读入，文件里没有一处硬编码的凭据（auth_db.py:8-13、auth_utils.py:11-13）。这一点比任何功能都重要，因为它决定了这份代码能不能被提交。

02架构

图上两条链是分开画的，因为它们真的没有连起来：请求链只走到模板，写库链只在建用户时走一次。这个「没有连起来」不是画图时的省略，而是当前的实情，第六节会说明它意味着什么。

表结构只有两张：users（id / username 唯一索引 / hashed_password，auth_db.py:23-27）与 user_config（user_id 索引 + 一个 JSONB 列，:29-33）。用 JSONB 而不是把配置拆成列，是因为配置项的集合本身还会变；代价是这些字段不能靠 SQL 约束保证形状，校验只能放在写入之前。

03关键决策与取舍

D1 · 连接池探活交给驱动

理由create_engine 带 pool_pre_ping=True 与 connect_timeout=3（auth_db.py:17）。取连接前先探活，数据库重启后池里的旧连接不会再变成一批 500；超时压到 3 秒，是因为一个连不通的库不该让请求挂到网关超时。

放弃每个请求自己 ping 的确定性。代价是每取一次连接多一次往返，这笔固定开销在低并发时看得见。

D2 · 会话按请求生成，不共享全局会话

理由sessionmaker(autocommit=False, autoflush=False)（auth_db.py:18），get_db() 用 yield 把会话交给依赖，finally 里关掉（:38-43）。自动提交关掉意味着提交是显式的，自动 flush 关掉意味着查询顺序不会意外触发写入。全局会话会让并发请求的事务互相污染。

放弃少写两行代码的便利。代价是每个写路径都必须记得 commit()，忘了就是「接口返回 200 但库没变」。

D3 · 密码与令牌分表，令牌不塞进用户行

理由hashed_password 列只存 bcrypt 哈希（auth_db.py:27，写入在 creat_user.py:13-16）；用户相关的可配置数据单独一张 user_config，用 user_id 关联（:31-33）。一个用户多份配置时，加行而不是改行。

放弃把令牌和配置都塞进用户行的省事。代价是取配置多一次查询，且没有外键约束——user_id 只是一个带索引的整数列，孤儿行由应用层负责。

04难点与解法

一 · 生成器依赖不能当对象用

get_db() 是 yield 出来的生成器（auth_db.py:38-43），它只有在 FastAPI 的依赖注入里才被「变成一个会话」。文件末尾那段 if __name__ == '__main__' 里写的是 db = get_db() 然后直接 db.add(user)（:48-50）——db 拿到的是生成器对象，add 会在第一次调用时抛 AttributeError。这段「测试代码」跑不起来，正确的写法是 db = SessionLocal() 或 next(get_db())。留着它是因为它演示了类的用法，但它不是可执行的验证。

二 · 密码怎么存与令牌怎么发是两件事

哈希不可逆，令牌可解析——混在一处最容易写成「把密码塞进 JWT」。代码把它们分在两个函数群里：hash_password / verify_password 走 CryptContext(schemes=["bcrypt"])（auth_utils.py:18、:22-28）；create_access_token 把 sub（用户 ID）、username 与 exp 放进载荷再签名（:32-41）。令牌里的内容是明文可读的，签名只保证它没被篡改，这一点在载荷里只放 ID 而不放敏感信息时才算安全。

三 · 解析失败要返回空值而不是抛异常

decode_token 用 try/except JWTError 包住 jwt.decode，过期或伪造一律返回 None（:43-50）。调用方只需要判空，不必区分「过期」与「签名不对」——把这两种情况都暴露给客户端，等于给攻击者一个试探签名的信道。

05代码走读

第一段是连接与会话。注意连接串那一行只留了占位——四段凭据全部来自环境变量，代码里不出现任何值：

load_dotenv()

DB_PASSWORD = os.getenv("DB_PASSWORD")
SERVER_IP   = os.getenv("SERVER_IP")
DATA_BASE   = os.getenv("DATA_BASE")
OWNER_NAME  = os.getenv("OWNER_NAME")

# 四段取自环境变量，这里不展开
SQLALCHEMY_DATABASE_URL = "postgresql+psycopg://…"

engine = create_engine(SQLALCHEMY_DATABASE_URL,
                       pool_pre_ping=True,                       # 取连接前探活
                       connect_args={"connect_timeout": 3})
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()


def get_db():
    db = SessionLocal()          # 每个请求一个会话
    try:
        yield db
    finally:
        db.close()               # 无论成功失败都关

第二段是鉴权工具。两个函数群各自完整，但共用同一个密钥来源：

SECRET_KEY  = os.getenv('SECRET_KEY')
ALGORITHM   = os.getenv('ALGORITHM')
ACCESS_TOKEN_EXPIRE_MINUTES = int(os.getenv('ACCESS_TOKEN_EXPIRE_MINUTES'))

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)

def create_access_token(user_id: int, username: str) -> str:
    expire = datetime.now(timezone.utc) + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    payload = {
        "sub": str(user_id),     # 只放 ID，不放密码或权限
        "username": username,
        "exp": expire,           # 过期时间
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

def decode_token(token: str) -> dict:
    try:
        return jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except JWTError:
        return None              # 过期或伪造都返回空，不向客户端区分

写入路径只有一条，在 creat_user.py:5-19：先 create_all 建表，再开一个会话，按用户名查重，查不到才哈希并插入，最后在 finally 里关闭。查重与插入之间没有加锁——并发建同名用户时由 users.username 的唯一索引兜底，代价是其中一个请求会拿到 IntegrityError 而不是干净的提示。

06失败与下一步

  • auth_db.py 末尾的测试块跑不起来。db = get_db() 得到的是生成器，db.add(user) 直接 AttributeError（:46-53）。它看起来像可运行的验证，实际上只是一段演示；真要验证得用 SessionLocal()。
  • 两种导入风格并存。creat_user.py:1-2 用的是扁平导入 from auth_db import ...，也就是说这个文件只能在该目录下直接 python creat_user.py 跑；而同一个人的另一个工程用的是包路径（project.fruit2.xxx）。同一批文件被两种约定切成了两半，谁都不能从仓库根一次性 python -m。
  • 鉴权层还没有被任何路由引用。live/main.py 只有一个 "/" 的模板路由（:9-12），没有 Depends(get_db)，也没有取 verify_password。125 行的鉴权与数据层目前是「可被引用的工具」，不是「被引用的能力」——图上两条链没有连起来，说的就是这件事。
  • 没有测试。139 行里没有一行断言。上面三个问题，任何一个都能被一个 pytest 文件在几秒内盯住。

下一步按性价比排序：① 写 tests/test_auth.py：哈希-校验往返、过期令牌返回 None、同名用户重复创建抛 IntegrityError——三个用例就能把第 1、3 条钉死；② 把 creat_user.py 换成包内相对导入，让它既能被 -m 调用也能被测试 import；③ 把 FastAPI 文档里的接口片段收敛成一个真正的 api.py：/register 与 /login 两条，用 Depends(get_db) 接上现有的会话与鉴权，至此两条链才真正连成一条。
