图像分类实验台

CV · Transfer Learning · PyTorch / torchvision / ONNX

换一个分类任务，最重复的动作是把 transforms、Dataset、训练循环、导出脚本各写一遍。这个工程把它们固定成一套骨架：主干与分类头分离，装配只在一处发生，训练、导出、单图推理调用同一份装配。

01任务与边界

目标不是把某一个分类器训到多高，而是交付一套换数据集就能用的骨架：数据从哪读、增强怎么做、主干怎么换成自己的、分类头在哪一行被替换、权重怎么存、怎么导成 ONNX、导完之后怎么用一张图验证它没变味。

边界写在入口里。整个工程只有三个模式，用同一个 LoadAll 装配（main.py:90-111）：

  • --mode 0 训练：train_data() 里依次调用 train_data_process → val_data_process → model_loader → switch() → weight_loader → trans_train_optimizer → trans_train_scheduler，然后才进 train(cfg, load)（main.py:8-35）。顺序不是装饰——优化器必须建在「可训练参数集合」确定之后。
  • --mode 1 验证：跑一遍 test 目录，输出总精确度（pred.py:15-62）。
  • --mode 2 单图：对目录里每张图输出 文件名 -> 预测类别（置信度）（pred.py:79-112）。
  • 不做的事：不做量化、不做蒸馏、不做推理服务化。导出就停在 .onnx 文件这一层。

配置集中在一个类里：setting()（config.py:5-89）。数据路径、超参、保存策略、续训开关全在 __init__ 的一次构造中定型，其余文件只读 cfg.xxx，不各自定义常量。

02架构

主链是产出一个权重文件；导出与推理是它的两条派生路径，复用同一份装配（同一个 LoadAll、同一次 switch()、同一份 state_dict）。这就是为什么 out_onnx.py 只有 45 行还能保证与训练一致。

四个目录各有分工：train 与 val 进训练循环，test 只在 --mode 1 用于报告总精确度，single 是一批散图，用于 --mode 2 逐张看结果（config.py:17-20）。类名不是手写的清单说了算，而是 ImageFolder(root=cfg.data_root).classes 从目录名读出来的（config.py:35）。

03关键决策与取舍

D1 · 主干与分类头分离，分类数是一个出口

理由model.py 里 5 个主干（GoogLeNet / ResNet / VGG / LeNet / AlexNet）都接在同一个概念上：num_classes（:100 / :224 / :355 / :430 / :508）。换主干只改 config.py:8 的一行，换数据集类别数只改 cfg.num_classes。

放弃「一个主干一个文件、各自写死输出层」的直观排布。代价是 518 行挤在一个文件里，且分类头的取法被统一假定成 .fc——这条假设在 ResNet 以外不成立，见第四节。

D2 · 训练与验证两套 transforms

理由训练侧 Resize + 水平翻转 + 旋转 + 颜色抖动 + 仿射 + 归一化；验证侧只有 Resize 与归一化（load.py:18-26 / :28-32）。验证侧做增强，指标就不是在真实分布上量的了。

放弃两侧共用一套的省事。代价是两个 Resize 尺寸得手动对齐，改 cfg.input_size 时两处都要看，没有任何机制替你把关。

D3 · 迁移学习用判别性学习率，并锁住 BatchNorm

理由分类头用 cfg.learning_rate，骨干用它的 1/100（load.py:184-187），因为随机初始化的头不该和 ImageNet 预训练的特征用同一个步长。freeze_bn() 把 BN 全部切到 eval 并停止统计（:147-156），训练循环每个 epoch 重新调一次（train.py:102-103）。

放弃全量微调的简单：现在只解冻 layer4 与 fc（load.py:137-140），模型容量被主动限制住，换到差异更大的数据集上会欠拟合。

04难点与解法

一 · switch() 只对 ResNet 成立

换分类头那几行写的是 self.model.fc = nn.Sequential(...)（load.py:131-134）。ResNet 的分类头确实叫 fc（model.py:224），但 VGG 与 AlexNet 把它放在 classifier 的最后一项里（:355 / :508）。所以「5 个主干共用同一个出口」在模型定义这一层是成立的，在装配这一层只跑通了 ResNet——这是我事后才看清的边界，不是设计时就想好的分层。

二 · 指标口径：不能把不满批当整批

准确率不是「每批正确率的平均」，那样最后一批样本少就会把权重算歪。训练与验证两侧都是按正确个数累加再除以本轮真实样本数：each_train_acc_total += torch.sum(pre_lab == b_y)、train_num += b_x.size(0)，最后 each_train_acc_total / train_num（train.py:144-146 / :170-177，验证侧 :180）。loss 同理先乘 b_x.size(0) 再加（:137），注释里写明了原因。

三 · 改了可训练集合就得重建优化器

解冻 layer4 之后，优化器里的参数组和第 0 轮时已经不是同一批对象了。所以每改变一次可训练集合就要新建优化器，并且不能加载旧的 optimizer_state_dict（load.py:171-174）；是否加载由 cfg.new 控制（:189-191）。续训时还要把优化器状态里的张量搬回模型所在设备（:206-210），否则 CPU 上训过再上 GPU 会直接报设备不一致。

05代码走读

第一段是两套 transforms。它们是这个工程里唯一「两边必须长得不一样」的地方，差异本身就是设计：

self.transforming_train = transforms.Compose([
    transforms.Resize((cfg.input_size, cfg.input_size)),
    transforms.RandomHorizontalFlip(p=0.5),
    transforms.RandomRotation(20),
    transforms.ColorJitter(brightness=0.2, contrast=0.2, saturation=0.2),
    transforms.RandomAffine(degrees=0, translate=(0.1, 0.1), scale=(0.8, 1.2)),
    transforms.ToTensor(),
    transforms.Normalize(mean=[0.485, 0.456, 0.406],   # ImageNet 均值
                         std=[0.229, 0.224, 0.225])])

self.transforming_val = transforms.Compose([
    transforms.Resize((cfg.input_size, cfg.input_size)),
    transforms.ToTensor(),
    transforms.Normalize(mean=[0.485, 0.456, 0.406],   # ImageNet 均值
                         std=[0.229, 0.224, 0.225])])

第二段是导出。它短到可以整段读完，但把三个容易出事的地方都显式写了出来：权重从 CPU 上读、model_state_dict 取不到就直接抛错、导完的图带动态 batch 维。

cfg = setting()
checkpoint = torch.load(cfg.load_path, map_location='cpu')   # 加载到 CPU，用 CPU 版 onnxruntime

load = LoadAll(cfg)
load.model_loader(cfg.model)
load.switch()                                                # 与训练用同一份装配：换掉分类头

state_dict = checkpoint.get("model_state_dict")
if state_dict is None:
    raise ValueError("checkpoint 里没有 model_state_dict，检查 key 名称")

load.model.load_state_dict(state_dict)
load.model = load.model.cpu()
load.model.eval()                                            # 必须 eval：BN 与 Dropout 才会定住

dummy_input = torch.randn(1, 3, 224, 224)

with torch.no_grad():
    torch.onnx.export(
        load.model, dummy_input, out_path, opset_version=12,
        input_names=["input"], output_names=["output"],
        dynamic_axes={"input": {0: "batch_size"}, "output": {0: "batch_size"}},
    )

注意 eval() 与 no_grad() 这两步：导出的是推理图，分类头里那个 Dropout(0.3)（load.py:132）如果在 train 模式下导出，ONNX 图里会带上随机性，推理端每次结果都不一样。

06失败与下一步

  • 类名有两份定义。一份是手写的 50 项 cfg.class_names（config.py:34），一份是 ImageFolder(...).classes（:35）。单图推理用的是后者（pred.py:108），所以真正决定标签的是目录名；两份清单一旦顺序不同，人眼看到的 class_names 会给出错误解释，而且没有任何断言会拦住它。
  • num_classes 被赋值两次。config.py:10 写 10，:38 又覆盖成 50。后者生效，读代码的人先看到 10 会得出相反结论。
  • 续训是三个整数开关。train_mode（0/1/2）、transfer_mode（0/1）、save_mode（0/1）决定加载哪份权重、要不要冻结 BN、覆盖还是追加保存（config.py:47-51，语义写在 :52-63 的注释里）。改错一个数字就换一种行为，没有校验。

下一步三件事，按顺序做：① 类名收敛成单点派生——class_names 只用于显示，加载时断言 len(class_names) == len(ImageFolder.classes)；② switch() 按主干名取分类头（fc / classifier[-1]），把「5 个主干共用出口」从模型层补到装配层；③ 把 --mode 0/1/2 拆成 argparse 子命令，顺便把三个整数开关换成枚举式的显式参数。
