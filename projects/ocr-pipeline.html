漫画 OCR 翻译管线

RapidOCR · OpenCV · Pillow · numpy · requests · FastAPI · Python 3 · 纯 CPU

一页漫画要变成可读的中文页，得先让机器把识别出来的文本框重新读回句子，批量送翻译，再把译文塞回原来的框里。难点不在识别率，在版面：文本框互相重叠、竖排与斜排混在同一页、一个气泡里的句子常被折成两三行。这条管线用 9 个 Python 文件 969 行，把这件事固定成一条能重复跑的命令。

01任务与边界

输入是一张漫画页图的路径，输出是同尺寸的重绘页。链路在 main.py 里按顺序写死：RapidOCR 给出文本框与识别文本 → block.py 按相邻关系把框并成块 → units.py 把块切成句 → trans.py 一次请求送多句译文 → change.py 擦掉原字、按框重排并写回。

边界和功能一样重要，下面这些事它明确不做：

  • 不做生成式修复。擦除走 cv2.inpaint，不加载修复模型。
  • 不做气泡检测。只处理 OCR 给出的文本框，不用语义去寻找对话气泡的轮廓。
  • 不做跨页拼接、不做色彩管理与导出格式转换，输出固定为同尺寸的 JPG。
  • 不在识别阶段训练或微调，RapidOCR 用预置模型；这一层被当成黑盒。
  • 不做语种选择，目标语言固定为简体中文。

边界收窄换来的是可复核：整条链只依赖四个库，每一步都能单独跑，某一步出错不会把前后步骤一起拖垮。

02架构

数据流是单向的，只有擦除与回填共享同一帧：识别结果先变成句子，句子变成译文，译文再回到原来的框。下图里青色是决定输出质量的路径，其余是普通搬运。

03关键决策与取舍

三个决策决定了这条链的形状；每一条都写清楚换掉了什么。

D1 · 按句翻译，不按块翻译

理由整块文本会超过翻译接口的单行上限，切句后每句独立，失败只影响一句。units.py 的 extract_units 给每句记 block_idx，regroup_blocks 再按它拼回原块。

放弃段落级语气的连贯——跨句的代词与语气词现在会各自独立翻译。

D2 · 擦除用 cv2.inpaint，不引生成式修复

理由change.py 的 Erase 走 mask 加 5×5 膨胀再 INPAINT_TELEA，不引入第二份权重，整条链在纯 CPU 上跑完，部署成本只有一个 Python 环境。

放弃复杂网点背景上的残影控制——网点、渐变底纹上仍会看到擦除痕迹。

D3 · 回填字号二分，不用固定档位

理由font.getmetrics() 让「折行后的总高」随字号单调上升，所以满足「总高 ≤ 框高」的最大字号可以二分求，循环里只排版、不绘制。

放弃几档固定字号的省事写法——那种写法在同一页里会明显浪费框内空间，长短译文看起来像两个字体。

04难点与解法

两个真正吃掉时间的点，都在回填这一步。

译文比原文长时溢出框。中文译文常比原文长三成。做法是先用 draw.textlength 逐字累加真实像素宽，在框宽 94% 处折行（change.py 的 _char_wrap），再二分找「折行后总高 ≤ 框高 94%」的最大字号；二分的上界直接由框高给出（封顶 120px），不靠试画。

批量返回的条数与输入对不上。trans.py 的 __call__ 先按行数相等直接对齐；不等就把多行译文重拼再切；仍不等则整批回落为逐条翻译，并把条数差异写进日志。units.py 还在切句时用 1,500 字符上限把超长单句再切一次，避免单条请求直接被接口拒绝。

  • 竖排与斜排各有一支绘制分支：_draw_vertical 逐字下移，_draw_rotated 旋转后绘制，字号仍来自同一套二分结果。
  • 文字颜色从框内像素反推（_text_color），浅底写深字，避免白底白字。

05代码走读

折行是二分的前置条件：只有「给定字号能算出确定行数」，字号与总高之间才有单调关系。这一段来自 change.py。

# change.py — 逐字符测量真实宽度后折行
def _char_wrap(self, text, font, draw, max_w):
    lines, cur = [], ""
    for ch in text:
        if draw.textlength(cur + ch, font=font) <= max_w or not cur:
            cur += ch
        else:
            lines.append(cur)
            cur = ch
    if cur:
        lines.append(cur)
    return lines or [""]

有了它，字号搜索就是标准二分：每次只加载候选字号并排版，判据是「行数 × 行高 ≤ 框高 × 0.94」。搜索区间固定为 6px 到 min(120, 框高)，最多七次迭代。

# change.py — 满足「折行后总高 ≤ 框高」的最大字号
lo, hi = 6, max(6, min(120, int(box_h)))
best = None
while lo <= hi:
    mid = (lo + hi) // 2
    font = self._load_font(mid)
    asc, desc = font.getmetrics()
    line_h = asc + desc
    lines = self._char_wrap(text, font, draw, box_w * 0.94)
    if lines and len(lines) * line_h <= box_h * 0.94:
        best = (mid, lines, line_h, asc)
        lo = mid + 1
    else:
        hi = mid - 1

06失败与下一步

已知缺陷，按影响排序：

  • 依赖外部翻译 API，凭据从环境变量读（BAIDU_APP_ID / BAIDU_SECRET_KEY）；离线环境整条链会停在 trans.py，没有本地模型兜底。
  • 批量条数对不上时整批回落逐条翻译：正确但慢，日志里只记条数差异，没记原因。
  • _char_wrap 不认词边界，英文与数字会在单词中间断开，中英混排页会出现断词。
  • 擦除在网点与渐变底纹上留残影；94% 的宽度与高度余量是手调常数，不是从字体度量推出来的。
  • 没有自动化测试：改动回填逻辑只能靠肉眼比对输出图，回归全靠人工。

下一步只做两件：给折行加英文断词规则；把一组固定页的输出图做成可哈希比对的回归集，让回填逻辑的每次改动都有对照。
