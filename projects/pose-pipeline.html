04 Archive / Pose inference

实时姿态估计推理管线

Real-time Inference · ONNX Runtime / TensorRT / Win32 / PySide6

一条每帧十来毫秒的管线：抓屏拿 BGRA，预处理成 NCHW，TensorRT 出一组人体框与关键点，后处理反解回屏幕坐标，最后整张位图贴到 Win32 分层窗口上。这一页讲的是这条链怎么把固定开销一段段削掉，以及哪些地方现在仍然不稳。

形态

规模

01任务与边界

要交付的不是一个模型，而是一条每帧都压在预算内的管线。输入是抓屏拿到的 BGRA 帧，输出是屏幕上一组骨架线和每个人体框对应的关键点坐标。介于两者之间的每一步都在预算里：预处理、推理、后处理、上屏。

边界划得很清：

  • 只管模型的那部分是 pose_forward.py：它的 docstring 第一句就写着「只管模型，不管屏幕、不管画图」，输出形状固定为 (1, 5 + NUM_KPT*3, 8400)——4 个框参数、1 个人体分数、每个关键点 3 个通道。
  • 只管窗口的那部分是 win32_overlay.py：它不知道什么叫关键点，只认一块 (h, w, 4) 的 BGRA 数组。
  • 只管串联的是 pose_overlay.py：抓屏线程做「抓帧 + 预处理」，主线程做「推理 + 反解 + 画 + 贴窗口」，两片 blob 缓冲区交接。
  • 不做的事：不做模型结构创新，不训练这一个具体任务之外的主干；只把已有的 YOLO pose 权重导出、跑起来、稳住。

关键点个数不硬编码在任何一行代码里——NUM_KPT = len(KEYPOINT_NAMES)（pose_forward.py:45）。换一套关键点定义只要改 config.py，推理文件里的数字一个都不用动；解码处还有一道断言，通道数对不上直接抛错而不是悄悄错位（:353-355）。

02架构

数据是单向流动的，能量守恒式的一进一出：屏幕上的像素进去，同一坐标系下的关键点出来。右侧两条支线是控制面（控制台启动与参数）和启动优化面（引擎缓存）。

线程模型的边界也在图上：抓屏线程只做能交给 CPU 又不碰 GPU 的那一段（preprocess()），主线程只做 GPU 与绘制。两条线程用 NBUFS = 2 组缓冲区交接（pose_forward.py:138），一边填第 N+1 帧的输入时，GPU 还在算第 N 帧。

03关键决策与取舍

D1 · 把预处理整体塞进模型

理由缩放 640 + BGRA→RGB + /255 + NCHW 打包这一段是 3.45 ms 纯 CPU（make_pre_model.py:5-6）。用 make_pre_model.py 生成一个直接吃原始 BGRA 帧的 ONNX，这几步全交给 GPU，CPU 只剩一次内存拷贝（约 0.4 ms），整帧 10.76 ms → 7.80 ms（config.py:22）。

放弃 cv2.dnn.blobFromImage 的通用性与一份模型的通用性——现在每个 REGION 各生成一个带尺寸后缀的文件，改完 REGION 必须重跑一次脚本，否则尺寸对不上会在 _alloc() 里直接抛错（pose_forward.py:268-274）。文件不存在时自动退回普通模型，不会崩。

D2 · 后端降级写死顺序，且降级必须出声

理由provider 列表固定为 TensorRT → CUDA → CPU（pose_forward.py:60-81），但降级不是默默的：_has_nvinfer() 先查 PATH 里有没有 nvinfer*.dll，因为一旦缺库，onnxruntime 会把 provider 降成 CPU 而不是 CUDA（:48-57），「悄悄变成 3 FPS」这种故障比启动失败更难查。

放弃「让框架自己决定」的省事：多写了三个分支和三条警告，换的是出问题时能从控制台输出直接读出实际 provider 列表（:158-164、:204-206）。

D3 · 覆盖层用 ctypes 写 Win32 分层窗口，而不是 UI 框架

理由内容整张位图经 UpdateLayeredWindow 提交，CreateDIBSection 把位图内存指针直接交给 numpy（win32_overlay.py:146-150，零拷贝），窗口带 WS_EX_TRANSPARENT 点击穿透 + WS_EX_TOOLWINDOW 不进任务栏 + WS_EX_NOACTIVATE 不抢焦点（:129-131）。内容由系统常驻保存，不走 WM_PAINT，所以切走再切回不会闪。

放弃跨平台：这份代码只能在 Windows 上跑，user32/gdi32 是硬依赖。

04难点与解法

一 · 每帧预算是逐项抠出来的，不是调出来的

慢在哪里要能分开算。文件顶部记着一组实测差值：先缩放再转色比反过来省 1.3 ms，手写 NCHW 打包比 blobFromImage 省 4 ms 且结果一位不差，中间缓冲区按输入尺寸复用一次，否则每帧重新 np.full 一个画布又是 1 ms（pose_forward.py:11-13）。这三条都落在 preprocess() 的十行里（:292-314），任何人「顺手改回去」都会把它们加回来。

二 · 纯推理 6.5 ms 里 GPU 只忙 28%

剩下全是每次调用的固定开销：kernel 启动、显存拷贝、同步。解法是把整张计算图一次性录成 CUDA Graph 回放，代价是输入输出地址必须固定，于是绑一块常驻显存的输入、每帧 update_inplace 覆盖数据（:208-227）。有一个反直觉的副作用：开了图之后必须配 IOBinding 走 run_with_iobinding，普通 run() 取不到输出——所以录制失败时会重建一个不开图的会话（:190-202），而不是留一个只能启动不能推理的对象。

三 · 定时器精度这类「不是算法的问题」

Windows 默认定时器精度约 15.6 ms，抓屏线程按 FPS 节流时 sleep 会忽长忽短，表现成帧龄一阵一阵地变大——卡顿感最直接的来源其实在这里（pose_overlay.py:31-34）。启动时的一次性处理清单是：timeBeginPeriod(1) 把定时器精度压到 1 ms、进程优先级提到 HIGH、OpenCV 关线程池、开跑后 gc.freeze() 并把阈值调大（:29-60）。这些都是给「每几百次分配就来一次的小停顿」交的保护费。

05代码走读

第一段是 provider 组装与回落。它决定了「这一次到底跑在什么上」，因此每一层都留了打印：

def _make_providers(trt, cuda_graph=False):
    """组装 provider 列表。trt=True: TensorRT -> CUDA -> CPU；否则 CUDA -> CPU。"""
    cuda = ("CUDAExecutionProvider", {"cudnn_conv_algo_search": "HEURISTIC"})
    if not trt:
        return [cuda, "CPUExecutionProvider"]
    opts = {
        "trt_engine_cache_enable": True,      # 不缓存的话每次启动都要重建引擎
        "trt_engine_cache_path": cache,
        "trt_timing_cache_enable": True,
        "trt_fp16_enable": bool(TRT_FP16),
        "trt_max_workspace_size": 2 << 30,      # 2GB 显存工作区（试过 4G，反而让 EP 起不来）
    }
    if cuda_graph:
        # 把整张图的 kernel 一次性录成 CUDA Graph，每次回放：纯推理 6.5ms -> 2.0ms。
        # 注意：开了这个就**必须**配 IOBinding 用 run_with_iobinding，普通 run() 会拿不到输出。
        opts["trt_cuda_graph_enable"] = True
    return [("TensorrtExecutionProvider", opts), cuda, "CPUExecutionProvider"]


# 申请了但没生效：显式退回 CUDA 重开，不静默降速（pose_forward.py:159-163）
used = s.get_providers()
if trt and "TensorrtExecutionProvider" not in used:
    print(f"[警告] TensorRT 申请了但没生效（实际 {used}），改用 CUDA 重开")
    s = ort.InferenceSession(path, options, providers=_make_providers(False))

第二段是每帧都要跑一次的预处理。写法上的刻意的：所有中间数组来自 _alloc() 建好的复用缓冲区，函数体里没有一次新的分配；几何参数跟着返回值一起走，不在 infer() 里读 self——因为两个线程同时在跑，不共享可变状态。

def preprocess(self, frame, i=0):
    """frame: uint8 (H, W, 4) BGRA（抓屏的原样输出）-> (NCHW blob, 反 letterbox 参数)。
    耗 CPU、不碰 GPU，所以单独拆出来给抓屏线程调用（和主线程的推理重叠）。"""
    h, w = frame.shape[:2]
    self._alloc(w, h)                      # 缓冲区按输入尺寸只建一次，之后每帧复用
    buf = self._bufs[i]
    if self.raw_input:
        # 只拷原始 BGRA（约 0.4ms），缩放 / 转色 / 归一化都在 GPU 里
        np.copyto(buf["raw"], frame)
        return buf["raw"][None], self._geo
    ratio, pad_x, pad_y = self._ratio, self._px, self._py
    x, y = int(self._px), int(self._py)
    # 先缩放到小图再转 RGB：转色只在小图上做，比"全尺寸转色再缩放"省一半
    cv2.resize(frame, (self._nw, self._nh), dst=buf["small"], interpolation=cv2.INTER_LINEAR)
    cv2.cvtColor(buf["small"], cv2.COLOR_BGRA2RGB, dst=buf["rgb"])
    buf["canvas"][y:y + self._nh, x:x + self._nw] = buf["rgb"]
    # HWC uint8 RGB -> NCHW float32 /255：等价于 blobFromImage，但快 4ms（实测结果一位不差）
    np.copyto(buf["blob"][0], buf["canvas"].transpose(2, 0, 1))
    np.multiply(buf["blob"], 1 / 255.0, out=buf["blob"])
    return buf["blob"], (ratio, pad_x, pad_y)

后处理那段同样值得看：_decode()（:349-383）先把 (1, 26, 8400) 转置、按置信度过滤，再算 NMS，最后把框和关键点一起减去 pad、除以 ratio 反解回原图坐标并裁到图内。裁边界这一步不做，覆盖层会在屏幕边缘画出界外的线。

06失败与下一步

  • 缺 nvinfer*.dll 时静默降级到 CPU。这不是假想：_has_nvinfer() 的 docstring 直接写着「否则整个 demo 悄悄变成 3 FPS」（pose_forward.py:52）。现在的对策是事先查 PATH 再决定要不要申请 TensorRT，并把实际 provider 打出来。
  • DLL 搜索路径只能改 PATH。os.add_dll_directory 实测无效，于是启动时手工把 site-packages 里的 nvidia/*/bin 与 tensorrt_libs 前置进 PATH（:22-36）；打包成单目录后又得改读 _internal/dlls。同一件事两套路径逻辑，是最容易在换机器时散掉的地方。
  • 没有自动回归。目前验「没跑偏」的办法是录制回放加人工比对：抓屏区域固定、按 15 fps 节流，存成 mp4（recorder.py:23-27）。没有一条命令能告诉你「今天的关键点比上周差了多少」。

下一步按代价从低到高：① 把 309 帧标注做成离线一致性回归——同一批帧跑两版引擎，输出人数、NMS 后框数、关键点偏移分布三张表，超过阈值就失败；② 把帧时间做成直方图而不是单值，记录 p50 / p95，因为「平均 7.8 ms」掩盖了抖动；③ 把 REGION 与 pre-model 尺寸的耦合收进一个生成步骤，改配置时自动重建而不是等运行期抛错。
