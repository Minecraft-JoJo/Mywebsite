扩散模型 LoRA 微调

kohya_ss · sd-scripts · TOML · bitsandbytes · PyTorch(CUDA) · uv · WSL

LoRA 微调真正花时间的不是训练，是复现：同一张图换分辨率、同一组超参换版本，结果就对不上。这里要的是一个把「数据集 → 配置 → 训练 → 采样」固定成文件的地方，而不是每次在图形界面里重新点一遍。整个外壳只有 1 个 Python 文件 91 行，训练本身交给上游的 sd-scripts；本地入口负责把环境搭起来、把每一次启动落成可重放的记录。

01任务与边界

它是一个外壳，不是训练框架。入口脚本 local_train.py 干四件事：把 bitsandbytes 按 cuda11x 编好装好、拉一份 kohya_ss、把工作目录切到固定位置、最后起 GUI；真正的训练由 sd-scripts 的 train_network.py 执行，采样由 sdxl_gen_img.py 执行，两者的输入是同一份 TOML。

边界同样要写清楚：

  • 不实现训练算法：UNet、VAE、文本编码器的前向与 LoRA 注入全在上游，这里是调用方。
  • 不量化采样质量：没有 FID、CLIP score 之类的指标，验证靠人眼比对同一组种子与提示词的输出。
  • 不做服务化：没有推理接口与任务队列，采样是本机的一次脚本执行。
  • 不托管权重：权重按 run 目录堆在本地磁盘，没有模型注册表与版本号。
  • 不做数据集标注：tag 由既有流程准备，delete.py 只按名单改写标签文件，不动图像本身。

边界的结果是：能复现的部分被固定成文件，不能复现的部分（CUDA、驱动、上游代码版本）暴露在脚本里，见第 6 节。

02架构

数据流是一条闭环：数据集与 tag 只进入配置生成；配置进训练，训练出权重，权重进采样；每次训练同时落一条运行记录，下一次配置从它出发。下图青色是决定产物的主路径。

03关键决策与取舍

三个决策都围绕同一件事：让「这次训练用了什么」事后还能读出来。

D1 · 参数落成 TOML 文件，不只存在界面里

理由kohya_gui 侧用 toml.dump 写盘（common_gui.py 的写配置分支，入口是 lora_gui.py 的 save_configuration）；训练与采样读同一份，改超参只改一处。

放弃「只在界面上保留一份临时参数」的便利：界面关掉之后，那些参数就不存在了。

D2 · 训练与采样分两个入口

理由sd-scripts/train_network.py 负责训练，sdxl_gen_img.py 负责采样；采样失败不用重训，换提示词也不用重新加载训练侧状态。

放弃一次启动两步走完：代价是两边各自加载一次底座模型，显存与时间都要付两遍。

D3 · tag 清理与训练分离

理由delete.py 只按名单改写数据目录下的标签文件、不动图像本身；先整理标签再起训练，避免训练中样本被删导致 dataloader 直接抛错。

放弃用通配符批量改标签的省事写法：一次手误就不可逆，而这里只改文本、可回滚。

04难点与解法

配置与权重必须成对。每次训练落 config_lora-20261001-080553.toml 与 last_20261001-080553.json 两份，文件名带同一个时间戳，权重与参数永远成对。任何「临时在命令行补一个参数」的做法都会让两份输入分叉，事后无法判断某组权重对应哪份配置，因此补参数必须回写到 TOML。

模板字段名与 sd-scripts 参数名来自不同层。配置模板由界面字段拼出，字段名对不上时错误在训练启动后才以解析失败的形式出现，而加载模型可能已经花掉几十秒。做法是每次改完模板先跑极小步数的一轮，确认能被解析，而不是等几十分钟后才失败。

  • 分辨率按 bucket 处理：640–1024、bucket 步长 16、batch 1。显存换分辨率覆盖，极端长宽比的图会被裁到最近的 bucket。
  • 精度与优化器绑定显卡代际：bf16 在 Ampere 以下没有硬件支持，AdamW8bit 依赖自行编译的 bitsandbytes，两者都是「换机器就重来」的环节。
  • 引导脚本用 os.path.exists 判断是否需要 clone，存在即跳过；这意味着换目录重跑和补装依赖是两件事，脚本只保证第一次。

05代码走读

local_train.py 一共 91 行，核心只有两个函数。执行外部命令用 shlex.split 切参数再交给 subprocess.Popen，不经过 shell 解释；stdout 与 stderr 合流后逐行转发，编译失败能立刻在终端看到。

# local_train.py — 外部命令按参数数组执行，输出逐行转发
def run_command(command):
    args = shlex.split(command, posix=(os.name != "nt"))
    process = subprocess.Popen(
        args, shell=False, stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True
    )
    for line in process.stdout:
        print(line, end="")
    process.wait()
    if process.returncode != 0:
        raise subprocess.CalledProcessError(process.returncode, command)

引导流程是四步直线：建工作目录、编译 bitsandbytes、拉 kohya_ss、起 GUI。下面省略了日志与注释，仓库地址已隐去。

# local_train.py — main() 的四步引导
base_dir = "kohya_local_setup"
os.makedirs(base_dir, exist_ok=True)
os.chdir(base_dir)

if not os.path.exists("bitsandbytes"):
    run_command("git clone -b 0.41.0 <bitsandbytes 仓库>")
os.chdir("bitsandbytes")
run_command("make cuda11x")
run_command("python setup.py install")
os.chdir("..")

if not os.path.exists("kohya_ss"):
    run_command("git clone -b v1.0 <kohya_ss 仓库>")
os.chdir("kohya_ss")
run_command("python kohya_gui.py --headless")

06失败与下一步

这套外壳解决的问题是「记录」，它没解决的问题是「环境」。已知缺陷按影响排序：

  • local_train.py 与 gui-uv.sh 职责重叠：两条路径都能起 GUI，一条负责装依赖、一条负责 clone，哪条先跑没有写进文档。
  • clone 锁到分支 tag（0.41.0 / v1.0），但 pip 依赖由 requirements 决定、没有哈希锁；半年后重跑可能装出另一套环境。
  • CUDA 版本写死在脚本里（make cuda11x），CUDA 12 的机器要改脚本才能过这一行。
  • 启动 GUI 那段被 try/except 包住并只 print 异常，脚本退出码仍是 0：从流水线角度看，启动失败也算「成功」。
  • 91 行里没有任何一步把训练实参写回 TOML：实参来自界面落盘的快照，脚本本身不校验两份是否一致。
  • 没有采样质量的量化口径，同一组种子的图只能靠人眼比。

下一步三件：引导改成带 lock 文件的可复现安装；启动失败返回非零退出码；每次 run 记录上游 git commit，让「哪份代码 + 哪份 TOML + 哪份权重」三者能对应上。
