01 ARCHIVE / OCR PIPELINE

漫画 OCR 翻译管线

Computer Vision · NLP · Render · RapidOCR / OpenCV / 翻译 API

01定位

RapidOCR 识别 → 版面分块重组 → 句级批量翻译 → 原字擦除与译文回填重绘的一条 Python 管线；9 个 Python 文件 969 行，依赖限定在 RapidOCR、OpenCV、Pillow、requests。

02问题

难点不在识别，在版面。文本框互相重叠，竖排与斜排混在同一页，一个气泡里的句子常被折成两三行；句子一错位，整页的阅读顺序就断了。翻译接口一次请求多行、一次返回，返回条数不保证等于输入行数，而回填必须让译文塞进原框且不溢出。

03架构

输入图 → RapidOCR → 版面分块重组 → 批量翻译 API → 擦除原字 / 二分字号回填 → 输出图

04关键决策与取舍

  1. D1

    句级翻译，不按块翻译

    理由整块文本会超过翻译接口的单行上限，切句后每句独立、失败只影响一句（units.py 的 extract_units 记录 block_idx，regroup_blocks 再拼回原块）。放弃段落级语气的连贯。

  2. D2

    擦除用 cv2.inpaint，不用生成式修复

    理由change.py 的 Erase 走 mask + dilate(5×5) + INPAINT_TELEA，不引入额外权重与 GPU，整条链纯 CPU 跑完。放弃复杂网点背景上的残影控制。

  3. D3

    回填字号用二分搜索，不用固定档位

    理由font.getmetrics() 让「折行后总高」随字号单调，可行字号可以二分（change.py:93），循环里只排版不绘制。放弃几档固定字号的省事写法，代价是框内空间浪费。

05难点与解法

  1. 译文比原文长时溢出框

    先按字符累加 draw.textlength，在框宽的 94% 内折行（change.py 的 _char_wrap），再二分找「折行后总高 ≤ 框高」的最大字号；二分上界由框高给出，不靠试画。

  2. 批量返回条数与输入对不上

    trans.py 先按行数相等直接对齐；不等就把多行译文重拼再切；仍不等则整批回落逐条翻译，并把条数差异写进日志。超长单句在 units.py 里按 1500 字符上限、以逗号与句号兜底再切。

02 ARCHIVE / TRAINING FRAMEWORK

自建 PyTorch 训练框架

Framework · Training · Export · PyTorch / ONNX / TensorBoard

01定位

把模型定义、数据管线、训练循环、配置、日志拆成五层的 PyTorch 骨架，3,012 行；训练、导出、推理共用一个参数对象，附带 ONNX 导出与用户鉴权。

02问题

手写训练脚本的通病是每换一个数据集就复制一份 train.py：增强、断点续训、日志路径全散在循环里。这里要解决的是「换数据集不碰训练循环」——配置、数据、模型、循环四者只通过参数对象通信；代价是任何一处字段改名都要同步四处。

03架构

cfg(yaml) → predata → model → train → logs(TensorBoard) / out_onnx · train → ckpt 续训

04关键决策与取舍

  1. D1

    配置做成参数对象（cfg/build_cfg.py 的 setting 类）

    理由训练、导出、推理拿到同一个对象，字段名一致；设备在构造时就选定 cuda 或 cpu。放弃dataclass 的类型检查，字段拼错要等运行时才报。

  2. D2

    日志目录按启动时间戳切分

    理由train/train_rnn.py:28 用 logs/tensorboard/{时间戳} 作 log_dir，同一份配置跑多次不互相覆盖，写入 Loss/train、Loss/val、Accuracy/train、Accuracy/val。放弃一个实验一个固定目录的整洁，代价是目录数随实验数增长。

  3. D3

    导出独立成 train/out_onnx.py

    理由训练进程不负责导出，checkpoint 是两者唯一的接口，导出失败不用重训。放弃训练结束自动导出的顺带便利。

05难点与解法

  1. ONNX 导出对 checkpoint 结构敏感

    先用 map_location=「cpu」载入，取 model_state_dict，取不到直接抛 ValueError；再 cpu()、eval()、no_grad 导出，opset 12，dynamic_axes 只放开 batch 维，输入输出按名固定。

  2. 断点续训从 start_epoch 起算

    循环写成 range(start_epoch, num_epochs + start_epoch)，轮次显示同步换算；两个 interrupted 权重路径分开写（train/train.py），避免中断时两份都不可用。

03 ARCHIVE / DIFFUSION LORA

扩散模型 LoRA 微调

Generative · Fine-tuning · kohya_ss / TOML / CUDA

01定位

kohya_ss 训练链的本地化外壳：数据集与 tag 整理、TOML 配置模板落盘、本地训练入口 91 行；训练与采样共用同一份参数，每次训练落一份配置快照。

02问题

LoRA 微调真正花时间的不是训练，是复现：同一张图换分辨率、同一组超参换版本，结果就对不上。需要一个把「数据集 → 配置 → 训练 → 采样」固定成文件的地方，而不是每次在图形界面里重新点一遍——界面里点的每一步都要能落回一次可重放的启动。

03架构

数据集 + tag → 配置模板(TOML) → kohya_ss 训练 → LoRA 权重 → 采样验证 · 训练 → 运行记录 json → 回到配置模板

04关键决策与取舍

  1. D1

    参数落成 TOML 文件，不止存在界面里

    理由kohya_gui/common_gui.py:1679 用 toml.dump 写盘，lora_gui.py:103 的 save_configuration 是入口；训练与采样读同一份，改超参只改一处。放弃只在界面上保留一份临时参数的便利。

  2. D2

    训练与采样分两个入口

    理由sd-scripts/train_network.py 训练，sdxl_gen_img.py 采样；采样失败不用重训。放弃一次启动两步走完，代价是两次各自加载一次底座模型。

  3. D3

    tag 清理与训练分离

    理由delete.py 只按名单改写 ./data 下的标签文件、不动图像本身；先整理标签再起训练，避免训练中样本被删导致 dataloader 直接抛错。放弃用通配符批量处理的省事。

05难点与解法

  1. 配置是唯一真相，改动必须回写

    界面里的 save_configuration 落 TOML 之后，训练与采样都读这一份；任何「临时在命令行补一个参数」的做法都会让两份输入分叉，事后无法判断某组权重对应哪份配置，所以每次训练落 config_lora-时间戳.toml 与 last-时间戳.json 两份，权重与参数永远成对。

  2. 模板字段错要几十秒内暴露

    配置模板由界面字段生成，字段名与 sd-scripts 的参数名来自不同层；每次改完模板先跑极小步数的一轮，确认能被解析，而不是等几十分钟后才在解析错误处失败。

04 ARCHIVE / POSE INFERENCE

实时姿态估计推理管线

Real-time Inference · ONNX Runtime / TensorRT / Win32 / PySide6

01定位

YOLO pose 权重 → ONNX 导出 → TensorRT 引擎缓存 → ONNX Runtime 会话 → Win32 分层覆盖层渲染的实时管线，5,604 行 31 个 Python 文件；控制台与录制器为 PySide6 与 dxcam。

02问题

这条链要在每帧十来毫秒里跑完预处理、推理、后处理、上屏。全流程跑通不等于稳：抖动来自每次调用的固定开销，不是算子本身；一次多余的整帧拷贝就能把预算吃掉一成。

03架构

pose 标注(309 帧) → 训练 → ONNX 导出 → 引擎缓存 → 运行时推理 → 覆盖层渲染 · 录制回归

04关键决策与取舍

  1. D1

    引擎缓存落盘

    理由TensorrtExecutionProvider 打开 trt_engine_cache_enable 并指定 trt_engine_cache_path（pose_forward.py:71-72），第二次启动不再重建引擎。放弃每次重建引擎与当前 GPU 完全匹配的确定性，换启动时间。

  2. D2

    预处理手写、顺序固定

    理由先缩放再转色、NCHW 打包手写、中间缓冲区按输入尺寸复用一次；文件顶部记着实测差异（转色顺序约 1.3ms，blobFromImage 约 4ms）。放弃cv2.dnn.blobFromImage 的通用性，换确定的每帧耗时。

  3. D3

    覆盖层用 ctypes 写 Win32 分层窗口

    理由内容整张位图经 UpdateLayeredWindow 提交，窗口带 WS_EX_TRANSPARENT 点击穿透与 WS_EX_TOOLWINDOW 不进任务栏（win32_overlay.py:25-31）。放弃跨平台。

05难点与解法

  1. 每帧预算

    整帧 10.76ms 降到 7.80ms，靠去掉 CPU 侧的一次整帧拷贝（pose_forward.py:168）；再把整张计算图录成 CUDA Graph 回放，纯推理 6.5ms → 2.0ms（:211-212）。TensorRT 没生效时明确退回 CUDA 并报出 provider 列表（:159-163），不静默降速。

  2. 覆盖层置顶与点击穿透

    WS_EX_LAYERED + WS_EX_TRANSPARENT + HWND_TOPMOST + WS_EX_NOACTIVATE，内容不走 WM_PAINT、由系统常驻保存整张位图；所以覆盖层不闪、不抢焦点、不挡鼠标。录制器固定抓屏区域、总取最新帧，用于回归。

05 ARCHIVE / CLASSIFIER BENCH

图像分类实验台

CV · Transfer Learning · PyTorch / torchvision / ONNX

01定位

数据集加载、迁移学习微调、验证指标、ONNX 导出与单图推理的完整闭环，1,495 行 8 个 Python 文件，作为分类任务的基准骨架。

02问题

换一个分类任务，最重复的动作是把 transforms、Dataset、训练循环、导出脚本各写一遍。实验台把这些固定下来：主干与分类头分离，装配只在一处发生，训练、导出、推理调用同一份装配。

03架构

数据集 → 加载器 → 迁移学习微调 → 验证指标 → ONNX 导出 → 单图推理

04关键决策与取舍

  1. D1

    主干与分类头分离

    理由model.py 里 5 个主干共用同一个 num_classes 出口（:100 / :224 / :355 / :430 / :508），换主干只改装配处。放弃一个主干一个文件的直观排布。

  2. D2

    训练与验证两套 transforms

    理由训练侧 Resize + RandomHorizontalFlip(0.5) + RandomRotation(20)，验证侧不增强（load.py:18 起）。放弃两侧共用一套的省事，代价是 resize 尺寸要手动对齐。

  3. D3

    导出与训练分两个脚本

    理由out_onnx.py 独立、带 dynamic_axes，推理端可以按需改 batch。放弃静态 shape 带来的导出期常量折叠。

05难点与解法

  1. checkpoint 与模型必须对齐才能导出

    out_onnx.py 显式检查 model_state_dict 是否存在，取不到直接抛错；再 cpu()、eval()、no_grad 导出，opset 12，input/output 名字固定，推理端按名取张量。

  2. 指标口径

    训练与验证的准确率按「批次正确数 / 本批样本数」累加（train.py 的 each_*_acc_total），不把最后一个不满批当整批；best_acc 与对应轮次一起存（maxacc_epoch），复盘时能定位到具体 checkpoint。

06 ARCHIVE / SERVICE LAYER

应用服务与数据层

Backend · Data · Auth · FastAPI / SQLAlchemy / PostgreSQL

01定位

FastAPI 服务模板 + SQLAlchemy 会话 + PostgreSQL + JWT/passlib 鉴权链；服务代码 139 行 5 个 Python 文件（users/ 4 文件 125 行 + live/main.py 14 行；live/1.py 42 行为草稿，不计入），另有 7,994 行 FastAPI 文档作为方法沉淀。

02问题

接口本身不难，难在连接与生命周期：数据库重启后连接池里的旧连接会变成一批 500；上传接口每次请求重新加载模型，会把内存和首字节一起拖住。鉴权还要分清「密码怎么存」和「令牌怎么发」。

03架构

HTTP 请求 → FastAPI 路由 → Pydantic 校验 → SQLAlchemy → PostgreSQL · 旁路 JWT/passlib 鉴权

04关键决策与取舍

  1. D1

    连接池探活交给驱动

    理由users/auth_db.py:17 的 create_engine 带 pool_pre_ping=True 与 connect_timeout=3，取连接前先探活，数据库重启不再批量 500。放弃每个请求自己 ping 的确定性，代价是每取连接多一次往返。

  2. D2

    重的对象放 lifespan

    理由OCR/api.py 在启动时构造一次模型与客户端，接口只做调用。放弃每请求独立初始化的隔离性，换常驻内存的稳定首字节。

  3. D3

    密码与令牌分表

    理由hashed_password 列存哈希（auth_db.py:27），令牌单独一张表用 user_id 关联（:31-33）。放弃把令牌塞进用户行的省事，代价是校验多一次查询。

05难点与解法

  1. 上传接口的依赖面

    FastAPI 接文件要有 python-multipart（OCR/api.py 顶部写明），缺了它报 422 而不是 500；接口用 UploadFile 而不是 bytes，避免整份文件进内存。

  2. 会话不共享

    sessionmaker(autocommit=False, autoflush=False)（auth_db.py:18），每个请求一个会话、显式提交、finally 关闭；全局会话会让并发请求的事务互相污染。
