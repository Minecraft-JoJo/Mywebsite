01 / WORKFLOW

工作方式

四条规则，顺序不换。

  1. 01

    先建最小可运行骨架，再补抽象

    每个工程先跑通一条最短路径：读一张图、跑一次前向、拿到一个结果。

    抽象只在第二处重复出现时才写，不为想象中的通用性提前付调试成本。

    证据 · projects/* · 6 个可独立运行的工程档案 · ls projects/*

  2. 02

    每个模块配一份文档，文档是交付物的一部分

    代码写完不等于交付完：接口、参数、坑与结论都写进 Markdown，和代码同仓。

    文档带行数与命令，别人可以按同一条路径复现，而不必先相信我。

    证据 · find . -name '*.md' | wc -l · 83 篇 / 52,594 行

  3. 03

    训练与推理分仓，导出格式当成一等产物

    训练侧只负责产出可验证的权重与 ONNX；推理侧只吃导出物与引擎缓存，不碰训练代码。

    导出失败就当成训练失败处理，因为下游真正消费的是那份文件，不是 checkpoint 本身。

    证据 · model / train / predata / cfg / logs 五层 · 训练框架 3,012 行，含 ONNX 导出与 TensorBoard 日志

  4. 04

    配置驱动：参数进 yaml / json，不进代码

    学习率、批大小、路径、模型名一律来自配置层或命令行入口，代码里不写死实验参数。

    换一组参数就是换一个文件，跑过的配置本身就是实验记录。

    证据 · cfg/ 配置层 + argparse 入口 · 见训练框架与分类实验台的 stack

04 / LIMITS

边界

写清楚不做什么，比列做过什么有用。

  • 01 / FRONTEND

    不做前端工程化框架

    这个站点是手写 HTML / CSS：零构建、无 npm 依赖、无打包器。以组件库、构建链为中心的交付不在范围内，交互复杂度也按手写成本设上限。

  • 02 / TRAINING

    不做大规模分布式训练

    现有工程都在单机、单卡上下文里：WSL CUDA、ONNX Runtime、TensorRT 引擎缓存。多机多卡调度与通信优化这一类，我没有可以展示的实做。
